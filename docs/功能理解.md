# ROS2 自主巡检项目：按功能链路理解

> 阅读方式：**不要一次从头看到尾**。平时忘掉其他文件，哪块模糊就只看对应的 1 个标题，每次 1～2 分钟就能把一条链路吃透。每个标题下，流程图里的 **`[1]` → `[2]` → ...** 与下方「按顺序走一遍」的 **`1.`、`2.`、...** 严格一一对应：先看图抓主线，再按同号步骤对照代码细节。

---

## 先认人：3 个角色与 4 个核心状态词

在看任何一条链路之前，先把整个系统记成 **3 个角色**：

1. **队长**（[mission.hpp](../src/patrol_manager/include/patrol_manager/mission.hpp)）：纯 C++17 大脑，**完全不懂 ROS2**。只负责根据规则做决定，并把要做的事写成小纸条放进盒子。
2. **传令兵**（[mission_node.cpp](../src/patrol_manager/src/mission_node.cpp)）：ROS2 适配层。用单线程执行器（`SingleThreadedExecutor`）串行处理所有回调，每 **50 ms** 调一次 `tick()` 问队长要干嘛，再把小纸条翻译成真正的 Nav2 调用、话题发布和 CSV 日志。
3. **司机 + 副驾刹车 + 车轮**（Nav2 + [guard.py](../src/patrol_sim/patrol_sim/guard.py) + [simulator.py](../src/patrol_sim/patrol_sim/simulator.py)）：Nav2 负责规划路线和输出速度；`velocity_guard` 像副驾安全员，只要没拿到“准行牌”或传感器断流就强制刹停；仿真底盘（或 Gazebo / 未来真机）负责真正移动并回报 `/odom` 与 `/scan`。

另外，队长脑子里最常出现的 **4 个状态变量**（几乎每条链路都会碰到）：

| 变量 | 大白话含义 |
|---|---|
| `active` | **手里正在干的这一单**（比如 `patrol/1` 或 `alarm-001`；空着表示当前无任务） |
| `flying` | **车是不是正在路上跑**（`true` = Nav2 正在带车赶路；`false` = 还没发车，或已到达原地停留中） |
| `cancelling` | **是不是正在等旧单子“刹停完”**（已喊 Nav2 取消，但还没收到 Nav2 的终结回调） |
| `token` | **发车单号**（每派一次新导航就 `+1`：1 号单、2 号单……用来防旧单子迟到的回调混进来） |

## 1. 队长怎么指挥传令兵（`Effect` 小纸条 + `drain()`）

**一句话作用**：把“业务规则”和“ROS2 通信”彻底拆开，让核心逻辑可以脱离 ROS2 单独测试和调试。

```text
[1] 任意事件进入 mission.hpp (submit / pause / tick / result / cancel_pending)
        │
        ▼
[2] 队长只做两件事：改状态变量 + 往 effects 盒子里塞小纸条 (Start / Cancel / Record)
        │
        ▼  (每 50 ms 由 mission_node.cpp 调用 drain() 倒出并清空)
[3] 传令兵按小纸条类型落地执行：
    ├── Start  ──→ start(e)  调 Nav2 发送导航目标
    ├── Cancel ──→ cancel()  调 Nav2 取消当前目标
    └── Record ──→ 发布 /patrol/records + 写入 records.csv + 打印终端日志
```

**按顺序走一遍**：
1. **任意事件进入 `mission.hpp`**：ROS2 层的各种输入（如收到报警调 `submit()`、暂停调 `pause()`、50 ms 定时调 `tick()`、Nav2 回调调 `result()`、撤销排队调 `cancel_pending()`）都会先转给纯 C++ 的队长对象 `mission_`，绝不在回调里直接操作 Nav2。
2. **队长只改状态 + 塞小纸条（`effects`）**：小纸条 `Effect::Kind` 只有 `Start`（发车）、`Cancel`（刹车）、`Record`（记账）3 种（[mission.hpp L28-L34](../src/patrol_manager/include/patrol_manager/mission.hpp#L28-L34)）。例如决定发车时（[mission.hpp L132-L134](../src/patrol_manager/include/patrol_manager/mission.hpp#L132-L134)），队长只会改 `flying = true`、`++token`，再往 `effects` 里塞 1 张 `Start` 纸条和 1 张 `"dispatched"` 的 `Record` 纸条。
3. **传令兵每 50 ms `drain()` 落地执行**：[mission_node.cpp L306-L322](../src/patrol_manager/src/mission_node.cpp#L306-L322) 调用 `mission_->drain()` 一次倒出所有纸条并清空盒子，再按 3 个分支分别执行 `start(e)`、`cancel()`，或发布 `/patrol/records` + 写入 `records.csv` + 打印终端日志。

**为什么这么设计**：
因为队长不碰任何 ROS2 API，所以在 [test_mission.cpp](../src/patrol_manager/test/test_mission.cpp) 写单元测试、或者用 GDB 调试 `cancel_pending` 时，根本不用起 Nav2 和仿真，几毫秒就能把所有状态切换跑完。

## 2. 系统启动与自动循环巡逻

**一句话作用**：拉起全部节点，确认定位与 Nav2 就绪后，按配置的航点一圈圈自动巡逻。

```text
[1] run.sh → run_system.py → system.launch.py (拉起底层仿真 + Nav2 + 业务节点)
        │
        ▼
[2] mission_node 每 50 ms tick()：自检 healthy() 且 nav_ready()
        │ 都就绪后
        ▼
[3] mission.hpp 选 patrol/<patrol_index> → 写 Start 纸条派发导航
        │ Nav2 到达回调 result_callback(SUCCEEDED)
        ▼
[4] 进入 DWELLING 停留满 patrol_dwell_sec → finish() 让 patrol_index++ 循环
```

**按顺序走一遍**：
1. **`run.sh` → `run_system.py` → `system.launch.py` 拉起全系统**：[run.sh L10](../scripts/run.sh#L10) 通过 [run_system.py L72-L74](../scripts/run_system.py#L72-L74) 启动 [system.launch.py L49-L97](../src/patrol_bringup/launch/system.launch.py#L49-L97)，按 `backend` 参数拉起底层（默认 `lightweight_sim` + 静态 TF `map→odom` + URDF；选 `gazebo` 时换成 TurtleBot3 + AMCL），再拉起 Nav2 6 大件、`mission_manager`、`velocity_guard` 和 `patrol_node`。
2. **`mission_node` 每 50 ms `tick()` 自检 `healthy()` 和 `nav_ready()`**：[mission_node.cpp L290-L305](../src/patrol_manager/src/mission_node.cpp#L290-L305) 确认两件事都为 `true` 才向队长传入 `ready = true`：
   - `healthy()`（[mission_node.cpp L201](../src/patrol_manager/src/mission_node.cpp#L201)）：收到过合法 `/odom`，且距离上次收到不足 `odom_timeout_sec`（默认 1 秒）。
   - `nav_ready()`（[mission_node.cpp L202](../src/patrol_manager/src/mission_node.cpp#L202)）：每秒轮询一次 `bt_navigator/get_state`，确认 Nav2 生命周期已进入 `ACTIVE`（state id = 3），且 `/navigate_to_pose` Action Server 就绪。
3. **`mission.hpp` 选 `patrol/<patrol_index>` 并写 `Start` 派发**：在 [mission.hpp L124-L135](../src/patrol_manager/include/patrol_manager/mission.hpp#L124-L135) 中，若 `ready` 满足且 `active` 与报警 `queue` 都为空，就按 `patrol_index` 从 [mission.yaml L5](../src/patrol_bringup/config/mission.yaml#L5) 取出对应航点，生成 `patrol/0`、`patrol/1`……发 `Start` 纸条。
4. **到达 → `DWELLING` 停留 → `finish()` 让 `patrol_index++` 循环**：
   - Nav2 到达后回调 `result_callback(SUCCEEDED)` → [mission.hpp L147-L148](../src/patrol_manager/include/patrol_manager/mission.hpp#L147-L148) 置 `flying = false`、`handling = true`，状态进入 `DWELLING`，记录 `arrived`。
   - 停留满 `patrol_dwell_sec`（默认 1 秒）后，下一次 `tick()`（[mission.hpp L119-L122](../src/patrol_manager/include/patrol_manager/mission.hpp#L119-L122)）调 [finish()](../src/patrol_manager/include/patrol_manager/mission.hpp#L195-L200)：记录 `completed`，`patrol_index = (patrol_index + 1) % waypoints.size()`，清空 `active`。下一拍回到第 3 步自动派发下一个点。

**为什么这么设计**：
`patrol_index` 只在**真正完成 (`finish()`)** 时才 `+1`。如果半路被报警抢占或暂停了，`patrol_index` 不变，恢复后会自动回到刚才没走完的那个巡逻点，不会漏点。

## 3. 速度控制与安全门禁（Nav2 → `velocity_guard` → 仿真底盘）

**一句话作用**：Nav2 算出的速度绝不直接发给车轮，必须过一层安全看门狗，保证“没许可、传感器断了、指令旧了”就立刻停车。

```text
[1] Nav2 算速并收口到 /nav_cmd_vel
    ├── 常规行驶：controller_server → /raw_cmd_vel → velocity_smoother → /nav_cmd_vel
    └── 脱困恢复：behavior_server → /nav_cmd_vel
        │
        ▼
[2] velocity_guard (guard.py) 20 Hz 看门狗校验与限幅
    检查 4 路输入：/nav_cmd_vel、/patrol/motion_permit、/odom、/scan
    (未获许可或任意一路超 0.5 s 未更新 → 输出 0；通过则限幅放行)
        │ /cmd_vel (底盘唯一速度出口)
        ▼
[3] lightweight_sim (simulator.py) 驱动底盘并回报传感器
    ├── 50 Hz step()：积分更新 (x, y, yaw) → 发 /odom + TF (odom → base_link)
    └── 10 Hz laser()：180 条射线求交 → 发 /scan (base_scan)
```

**按顺序走一遍**：
1. **Nav2 速度输出全部收口到 `/nav_cmd_vel`**：[system.launch.py L82-L90](../src/patrol_bringup/launch/system.launch.py#L82-L90) 把 `controller_server` 重映射到 `/raw_cmd_vel`，`velocity_smoother` 接 `/raw_cmd_vel` 输出 `/nav_cmd_vel`，`behavior_server` 也重映射到 `/nav_cmd_vel`，让 `velocity_guard` 成为唯一能往 `/cmd_vel` 发速度的节点。
2. **`velocity_guard` 汇聚四路输入做校验与限幅**：[guard.py L22-L28](../src/patrol_sim/patrol_sim/guard.py#L22-L28) 以 20 Hz 调 [guard_logic.py L24-L29](../src/patrol_sim/patrol_sim/guard_logic.py#L24-L29)：
   - `/patrol/motion_permit` 由 `mission_manager` 每 50 ms 通过 [publish_permit()](../src/patrol_manager/src/mission_node.cpp#L227-L229) 发布，只有同时满足 `flying && !cancelling && !paused && fault.empty() && healthy() && nav_ready()` 时才为 `true`；
   - 只要 `permitted == false`，或者 `/nav_cmd_vel`、`/patrol/motion_permit`、`/odom`、`/scan` **任意一路超过 0.5 秒没更新**，立刻输出 `(0, 0)` 停车；放行时把线速度限幅在 `±0.26 m/s`、角速度限幅在 `±1.0 rad/s` 后发到 `/cmd_vel`。
3. **`lightweight_sim` 驱动底盘并回报 `/odom` 与 `/scan`**：[simulator.py L41-L73](../src/patrol_sim/patrol_sim/simulator.py#L41-L73) 收到 `/cmd_vel` 后，50 Hz `step()` 用 [geometry.py L36-L45](../src/patrol_sim/patrol_sim/geometry.py#L36-L45) 的 `integrate()`（带防穿墙碰撞检测）更新位姿发 `/odom` 和 `odom→base_link` TF；10 Hz `laser()` 用 `raycast()` 算出 180 束激光发 `/scan`（`base_scan`）喂回给 Nav2 和 `velocity_guard`。

**为什么这么设计**：
上层调度和看门狗完全不依赖具体底盘。切到 `backend:=gazebo` 或未来接树莓派真机时，只要替换最底下吃 `/cmd_vel`、吐 `/odom` 和 `/scan` 的那一层，上面整套导航和安全链一字不改。

## 4. 报警接入、校验、去重与排队

**一句话作用**：把外部发来的报警先过两道安检（格式安检 + 业务安检），合格的放进优先队列等调度，不合格或重复的留下审计记录。

```text
[1] 外部发 /patrol/incidents → mission_node::on_incident()
    计数 + 查 frame=="map" + 查四元数归一化 → 不通过记 rejected；通过则转 yaw
        │
        ▼
[2] mission_->submit(task, now)
    查字段范围 + 查 known 去重 + 查队列上限 → 入 queue → 记 accepted
        │
        ▼  (排队等待调度期间)
[3] 每次 tick() 开头扫描 queue
    超过 expires (now + ttl_sec) 仍未派发的报警移除并记 expired
```

**按顺序走一遍**：
1. **`mission_node::on_incident()` 做 ROS 层安检**：收到 `/patrol/incidents` 后，[mission_node.cpp L207-L226](../src/patrol_manager/src/mission_node.cpp#L207-L226) 先把 `incident_received_count_` 加 1，再检查两点：
   - `target.header.frame_id` 必须是 `map`；
   - 四元数模长平方必须在 `1 ± 0.05` 范围内。
   - 不合格直接记 `rejected` 返回；合格则把四元数转成 `yaw`，交给 `mission_->submit()`。
2. **`mission_->submit()` 做业务层安检、去重与入队**：[mission.hpp L62-L77](../src/patrol_manager/include/patrol_manager/mission.hpp#L62-L77)：
   - 校验 `id` 非空（长度 ≤ 128 且不能以 `patrol/` 开头）、`priority` 在 `1~100`、`ttl_sec` 与 `handling_sec` 合法；
   - 查 `known` 集合：出现过的 ID 直接记 `duplicate` 忽略（进程内去重）；
   - 查队列长度与历史 ID 数量上限（`max_queue=64`, `max_ids=10000`）；
   - 全部通过：记入 `known`，计算绝对过期时间 `expires = now + ttl_sec`，分配递增序号 `order = ++sequence`（保证同优先级先进先出），塞进 `queue`，记 `accepted`。
3. **每次 `tick()` 开头清理排队过期报警**：在报警排队等待调度期间，每次 `tick()` 开头（[mission.hpp L104-L107](../src/patrol_manager/include/patrol_manager/mission.hpp#L104-L107)）会扫描 `queue`，超过 `expires` 还没派发的报警会被移除并记 `expired`。

**为什么这么设计**：
`on_incident()` **只负责入队，绝不直接发导航**。所有“要不要抢占、什么时候发车”全部统一收口到 50 ms 一次的 `tick()` 里判断，状态流转只有唯一入口，不会乱套。

## 5. 高优先级抢占、取消屏障与断点续巡

**一句话作用**：正在跑低优先级任务（巡逻或低优报警）时，如果队列里出现更高优先级报警，必须先安全刹停并确认旧导航彻底结束，再发新目标，做完后再接着干原来的事。

```text
[1] tick() 发现 best()->priority > active->priority，触发抢占
        │
        ▼
[2] suspend("preempt") 挂起当前任务
    ├── 正在路上 (flying)：cancelling=true + 写 Cancel 纸条 + 立刻断 motion_permit 刹停
    └── 原地处理 (handling)：直接退出 handling 并 requeue_active()（跳过 [3][4]）
        │ (若进入 cancelling)
        ▼
[3] 取消屏障：cancelling==true 期间 tick() 直接 return（超 3 s 触发 FAULT）
        │ Nav2 回调旧目标 result_callback
        ▼
[4] 核对 token → mission_->result() 清空 flying/cancelling + requeue_active() 放回原任务
        │ 下一拍 tick() 屏障解除
        ▼
[5] 从 queue 挑最高优报警 → ++token → 写 Start 纸条派发 → 完成后自动恢复原任务
```

**按顺序走一遍**：
1. **`tick()` 发现更高优先级报警，触发抢占**：[mission.hpp L116-L118](../src/patrol_manager/include/patrol_manager/mission.hpp#L116-L118) 比较 `best()->priority > active->priority`（巡逻默认优先级 0，报警 1～100；同优先级按 `order` 先来后到）。满足条件就调用 [suspend(now, "preempt")](../src/patrol_manager/include/patrol_manager/mission.hpp#L172-L179)。
2. **`suspend("preempt")` 按当前状态挂起任务**：
   - 若车正在路上（`flying == true`）：把 `cancelling = true`，塞 1 张 `Effect::Cancel` 纸条（同时当拍 `permit()` 变 `false`，`velocity_guard` 瞬间刹停底盘）。
   - 若车已经停在原地处理中（`flying == false`, `handling == true`）：不用向 Nav2 发取消，直接退出 `handling` 并 `requeue_active()`（跳过第 3、4 步，下一拍直接走第 5 步）。
3. **取消屏障等待旧导航终结**：只要 `cancelling == true`，[mission.hpp L108-L113](../src/patrol_manager/include/patrol_manager/mission.hpp#L108-L113) 每次 `tick()` 都会直接 `return`，绝不抢发新目标；如果超过 `cancel_timeout_sec = 3s` 还没收到 Nav2 回复，就触发 `FAULT` 锁存。
4. **旧目标回调核对 `token` 并放回原任务**：Nav2 回调 [result_callback](../src/patrol_manager/src/mission_node.cpp#L253-L256) → 核对 `token == mission_->token` → 调 [mission_->result()](../src/patrol_manager/include/patrol_manager/mission.hpp#L136-L145) 清除 `flying` 和 `cancelling`，再调 [requeue_active()](../src/patrol_manager/include/patrol_manager/mission.hpp#L180-L184)：
   - 若被抢占的是**低优报警**：原样放回 `queue`（支持多层嵌套抢占，高优做完再回来做它）；
   - 若被抢占的是**巡逻点**：清空 `active`，但 `patrol_index` 不动，等所有报警清空后自动接着跑这个巡逻点。
5. **下一拍 `tick()` 派发新目标，完成后恢复原任务**：屏障解除后，[mission.hpp L124-L135](../src/patrol_manager/include/patrol_manager/mission.hpp#L124-L135) 从 `queue` 挑选最优报警，`++token` 后发出 `Effect::Start`；等所有高优报警都完成后，原任务自动接续执行。

**为什么这么设计**：
如果不等旧 Action 终结就发新目标，旧目标迟到的 `SUCCEEDED / CANCELED` 回调很容易把新任务的状态冲坏。**取消屏障 + 递增 `token`** 是双保险：屏障保证同一时间 Nav2 里最多只有 1 个活目标，`token` 保证哪怕网络延迟送来旧回调也会被立刻丢弃。

## 6. 排队报警撤销（`cancel_pending`）

**一句话作用**：把还在 `queue` 里排队、尚未开始执行的报警撤掉，同时绝不误伤正在执行的任务，也防止同一个 ID 被重复提交。

```text
[1] 外部调用 /patrol/cancel_pending 服务（CancelPending.srv，传入 id）
        │
        ▼
[2] mission_node::cancel_pending_service_ 回调转发给 mission_->cancel_pending(req->id)
        │
        ▼
[3] mission.hpp 只在 queue 中查找该 id
    ├── 找到 ──> queue.erase() 删除 + 记 pending_cancelled + 返回 true
    └── 找不到（含正在 active 中）──> 不改任何状态 + 返回 false
```

**按顺序走一遍**：
1. **外部发起 `/patrol/cancel_pending` 服务请求**：服务接口由 [CancelPending.srv](../src/patrol_interfaces/srv/CancelPending.srv) 定义（请求 `string id`，响应 `bool success` / `string message`），外部可通过 `ros2 service call /patrol/cancel_pending "{id: 'alarm-001'}"` 发起撤销。
2. **`mission_node` 服务回调转发**：[mission_node.cpp L129-L137](../src/patrol_manager/src/mission_node.cpp#L129-L137) 收到请求后直接转发给 `mission_->cancel_pending(req->id)`，并把结果写入响应。
3. **`mission.hpp` 只在 `queue` 中按 `id` 删除**：[mission.hpp L79-L89](../src/patrol_manager/include/patrol_manager/mission.hpp#L79-L89) 只遍历 `queue` 查找匹配 `id`：
   - 找到：用 `queue.erase(it)` 移除该项，写一条 `pending_cancelled` 记录，返回 `true`（其余排队任务顺序不变）；
   - 没找到（包括这个 ID 正好是 `active` 活动任务）：不改任何状态，直接返回 `false`。

**为什么这么设计**：
撤销时**故意不从 `known` 集合里删掉这个 ID**——撤销代表“这一单作废了”，不能让旧消息重放又把它重新塞进队列；同时不碰 `active`，把“撤销排队”和“中断当前导航”的边界划清。

## 7. 导航进度反馈与首帧距离修复（`FeedbackPath`）

**一句话作用**：在导航行驶期间按合适频率打印剩余距离，并且解决目标刚切换时 Nav2 首帧 `distance_remaining` 混用上一条路径的问题。

```text
[1] start() 派发新目标，绑定目标“指纹”
    feedback_path_.reset(token, goal_stamp, "map", goal_xy)
        │
        ▼
[2] Nav2 发布 /plan，只接收当前目标的新路径
    feedback_path_.update(...)：校验 token/时间/坐标系/终点≤0.5m，预计算 suffix_
        │
        ▼
[3] Nav2 回调 feedback_callback，计算并打印剩余距离
    4 条件防旧回调 → 分级限频 (报警 1s / 巡逻 5s) → 投影算剩余距离并打印
```

**按顺序走一遍**：
1. **`start()` 发车时 `reset()` 绑定“指纹”**：[mission_node.cpp L242-L245](../src/patrol_manager/src/mission_node.cpp#L242-L245) 在 `start()` 里重置限频时间，并把当前 `token`、发车时间戳 `goal_stamp`、坐标系和目标点交给 [feedback_path_.reset()](../src/patrol_manager/include/patrol_manager/feedback_path.hpp#L19-L22)。
2. **订阅 `/plan` 调 `update()` 只收当前目标路径**：[mission_node.cpp L108-L118](../src/patrol_manager/src/mission_node.cpp#L108-L118) 收到全局路径 `/plan` 后调用 [feedback_path.hpp L24-L38](../src/patrol_manager/include/patrol_manager/feedback_path.hpp#L24-L38)：
   - 只有满足“`token` 匹配 + 路径时间戳晚于发车时间且更新 + 坐标系匹配 + 路径终点距目标 ≤ 0.5 m”才会被接受，同时倒着预计算每个路径点到终点的累积距离 `suffix_`。
3. **`feedback_callback` 过滤、限频并投影算距**：[mission_node.cpp L257-L284](../src/patrol_manager/src/mission_node.cpp#L257-L284)：
   - **4 条件防旧回调**：`token != mission_->token || !flying || cancelling || !active` 直接扔掉；
   - **分级限频**：报警每秒最多打 1 次，普通巡逻每 5 秒打 1 次；
   - **投影算剩余距离并打印**：调 [feedback_path.hpp L40-L63](../src/patrol_manager/include/patrol_manager/feedback_path.hpp#L40-L63)，若新路径还没来（或位姿时间戳早于新路径），只打印一次 `WAITING_FOR_CURRENT_PLAN` 且不消耗限频窗口；就绪后把当前位置投影到最近折线段，算出 `点到线段距离 + 该段剩余 + suffix_[i+1]` 并打印 `source=current_plan`。

**为什么这么设计**：
`/plan` 话题本身不带 Action UUID，Nav2 刚切换目标时反馈里可能短暂带着上一条路径的长度。用“时间戳 + 终点容差”把 `/plan` 和当前 `token` 对齐，且明确只用于进度显示、不参与到达判定，既准确又不影响安全逻辑。

## 8. 旁路状态观察与摘要（`patrol_node`）

**一句话作用**：独立于主调度节点的轻量监控节点，专门听主系统状态并对外提供人类易读的 1 Hz 摘要和计数清零服务。

```text
[1] mission_manager 每 50 ms 发布 /patrol/status
        │
        ▼
[2] patrol_node::on_status() ──> status_received_count_++ + 缓存 last_status_ + 仅状态名变化时打印
        │
        ├── [3] 1 Hz 定时器 publish_summary() ──> 发布 /patrol/summary ("NO_STATUS" 或状态快照)
        └── [4] /patrol/monitor/reset_count   ──> 只清零 status_received_count_，保留 last_status_ 缓存
```

**按顺序走一遍**：
1. **`mission_manager` 每 50 ms 发布 `/patrol/status`**：[mission_node.cpp L325-L330](../src/patrol_manager/src/mission_node.cpp#L325-L330) 在每次 `tick()` 末尾组装当前状态快照并发布。
2. **`patrol_node::on_status()` 计数、缓存与去重打印**：[patrol_node.cpp L67-L83](../src/patrol_manager/src/patrol_node.cpp#L67-L83) 收到消息后累加 `status_received_count_`、缓存最新快照 `last_status_`，只有当 `m->state != last_state_` 时才打印一条日志，避免 20 Hz 刷屏。
3. **1 Hz 定时器 `publish_summary()` 发布 `/patrol/summary`**：[patrol_node.cpp L86-L98](../src/patrol_manager/src/patrol_node.cpp#L86-L98) 每秒发布一次摘要；连上主系统前输出 `NO_STATUS`，连上后输出 `state=... active_id=... queue_size=... received=...`。
4. **`/patrol/monitor/reset_count` 清零计数**：[patrol_node.cpp L41-L52](../src/patrol_manager/src/patrol_node.cpp#L41-L52) 提供 `std_srvs/srv/Trigger` 服务，只把 `status_received_count_` 归零，保留 `last_status_` 防止摘要退回 `NO_STATUS`。

**为什么这么设计**：
旁路观察节点哪怕挂了、重启了，也完全不会影响 `mission_manager` 和 Nav2 的正常运行；这也是 ROS2 松耦合架构的典型用法。

## 9. 故障保护、急停锁存与人工恢复（`trip` / `recover`）

**一句话作用**：一旦发生影响安全的异常，立刻锁死系统并停车，绝不自动“瞎试”，必须等硬件/Nav2 恢复健康后由人工显式解锁。

```text
[1] 任意安全异常触发故障 (odom超时 / Nav2掉线 / 人工急停 / 日志写失败 / 取消超时 / 巡逻重试耗尽)
        │
        ▼
[2] 锁存 fault + 立刻断 motion_permit 刹停 + 必要时 suspend("fault") 取消导航（故障期间绝不自愈）
        │ 等传感器与 Nav2 恢复正常，且旧导航彻底终结 (!flying && !cancelling)
        ▼
[3] 人工调用 /patrol/recover ──→ mission_->recover() 全部门槛满足后清空 fault（保留 paused）
```

**按顺序走一遍**：
1. **任意安全异常触发故障**（只锁存第一个故障原因，后续故障不会覆盖它）：
   - 通过 `mission_->trip()` 触发：`/odom` 断流超 1 秒（[mission_node.cpp L303](../src/patrol_manager/src/mission_node.cpp#L303)）、导航中 Nav2 生命周期或 Action Server 掉线（[mission_node.cpp L304](../src/patrol_manager/src/mission_node.cpp#L304)）、人工调用 `/patrol/emergency_stop`（[mission_node.cpp L138-L142](../src/patrol_manager/src/mission_node.cpp#L138-L142)）、CSV 审计日志写入失败（[mission_node.cpp L323](../src/patrol_manager/src/mission_node.cpp#L323)）。
   - 队长内部直接锁存 `fault`：取消导航超 3 秒无回应（[mission.hpp L109-L111](../src/patrol_manager/include/patrol_manager/mission.hpp#L109-L111)）、巡逻点导航失败重试用完（[mission.hpp L190-L193](../src/patrol_manager/include/patrol_manager/mission.hpp#L190-L193)，不静默跳过）。
2. **锁存 `fault` + 断 `motion_permit` + 取消导航**：[mission.hpp L95-L98](../src/patrol_manager/include/patrol_manager/mission.hpp#L95-L98) 记录 `fault` 原因并调用 `suspend(now, "fault")`；只要 `fault` 非空，`permit()` 立刻变 `false` 让 `velocity_guard` 刹停，且 `tick()`（[mission.hpp L115](../src/patrol_manager/include/patrol_manager/mission.hpp#L115)）直接返回、绝不自愈。
3. **人工调用 `/patrol/recover` 过门槛解锁**：[mission_node.cpp L150-L154](../src/patrol_manager/src/mission_node.cpp#L150-L154) → [mission.hpp L99-L102](../src/patrol_manager/include/patrol_manager/mission.hpp#L99-L102) 必须同时满足 `healthy() && nav_ready() && !flying && !cancelling` 才允许清空 `fault`。并且清空 `fault` 时**不会改动 `paused`**（如果之前手动暂停了，恢复故障后仍保持暂停，防止车突然窜出去）。

**为什么这么设计**：
这是工业机器人典型的 **Fail-Safe（故障导向安全）** 原则：异常发生时第一时间断动力，且永远由人确认现场安全后再按恢复键。

## 10. 按 `Ctrl+C` 时的优雅退出

**一句话作用**：防止直接强杀进程导致 Nav2 生命周期节点报错卡死、或底盘还带着残留速度继续滑行。

```text
[1] 终端按 Ctrl+C ──→ 被 run_system.py 拦截（ros2 launch 在独立会话中，不被瞬间拍死）
        │
        ▼
[2] 循环调用 /patrol/prepare_shutdown ──→ 暂停任务 + 断 motion_permit + 等到 !mission_->flying
        │
        ▼
[3] 调用 lifecycle_manager_patrol/manage_nodes (SHUTDOWN) ──→ 按逆依赖顺序关闭 Nav2 6 大件
        │
        ▼
[4] 向 ros2 launch 发 SIGINT（超时再 SIGTERM / SIGKILL）+ guard.py 退出前补发全零 /cmd_vel
```

**按顺序走一遍**：
1. **`run_system.py` 拦截 `Ctrl+C`**：[run.sh L10](../scripts/run.sh#L10) 启动监管脚本 [run_system.py L59-L91](../scripts/run_system.py#L59-L91)，它把 `ros2 launch` 放在独立会话（`start_new_session=True`）里跑，所以按 `Ctrl+C` 时信号先到 `run_system.py`，不会一下子把所有 ROS 上下文同时拍死。
2. **循环调用 `/patrol/prepare_shutdown` 停业务**：[run_system.py L46](../scripts/run_system.py#L46) 反复调用 `/patrol/prepare_shutdown`（[mission_node.cpp L143-L149](../src/patrol_manager/src/mission_node.cpp#L143-L149)），先暂停并断掉 `motion_permit`，只有当 `!mission_->flying`（旧 Action 已拿到终结结果）才返回 `success = true`。
3. **调用 `lifecycle_manager_patrol/manage_nodes` 逆序关 Nav2**：[run_system.py L47-L52](../scripts/run_system.py#L47-L52) 通知 `lifecycle_manager_patrol` 执行 `SHUTDOWN`，让 Nav2 按逆依赖顺序销毁 BT 和控制器。
4. **发 `SIGINT` 结束 `ros2 launch` 并补零停车**：[run_system.py L90-L103](../scripts/run_system.py#L90-L103) 向 `ros2 launch` 发 `SIGINT`（超时依次升级 `SIGTERM` / `SIGKILL`）；同时 [guard.py L52-L55](../src/patrol_sim/patrol_sim/guard.py#L52-L55) 退出前还会再补发一帧全零 `Twist()` 给 `/cmd_vel` 确保底盘停稳。

**为什么这么设计**：
如果在 Nav2 正在执行导航时直接 `SIGINT` 强杀，BT 行为树和控制器常会因为上下文已销毁而抛出大量异常甚至僵尸进程。先“停业务 → 关 Nav2 → 杀 launch”有序收尾，退出干净利落。

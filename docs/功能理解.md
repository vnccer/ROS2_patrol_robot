# ROS2 自主巡检项目：按功能链路理解

> 阅读方式：**不要一次从头看到尾**。平时忘掉其他文件，哪块模糊就只看对应的 1 个标题，每次 1～2 分钟就能把一条链路吃透。

---

## 先认人：3 个角色与 4 个核心状态词

在看任何一条链路之前，先把整个系统记成 **3 个角色**：

1. **队长**（[mission.hpp](../src/patrol_manager/include/patrol_manager/mission.hpp)）：纯 C++17 大脑，**完全不懂 ROS2**。只负责根据规则做决定，并把要做的事写成小纸条放进盒子。
2. **传令兵**（[mission_node.cpp](../src/patrol_manager/src/mission_node.cpp)）：ROS2 适配层。用单线程执行器（`SingleThreadedExecutor`）串行处理所有回调，每 **50 ms** 调一次 `tick()` 问队长要干嘛，再把小纸条翻译成真正的 Nav2 调用、话题发布和 CSV 日志。
3. **司机 + 副驾刹车 + 车轮**（Nav2 + [guard.py](../src/patrol_sim/patrol_sim/guard.py) + [simulator.py](../src/patrol_sim/patrol_sim/simulator.py)）：Nav2 负责规划路线和输出速度；`velocity_guard` 像副驾安全员，只要没拿到“准行牌”或传感器断流就强制刹停；仿真底盘（或 Gazebo / 未来真机）负责真正移动并回报 `/odom` 与 `/scan`。

另外，队长脑子里最常出现的 **4 个状态变量**（几乎每条链路都会碰到）：

| 变量 | 大白话含义 |
|---|---|
| `active` | **手里正在干的这一单**（比如 `patrol/1` 或 `alarm-001`；空着表示当前无任务） |
| `flying` | **车是不是正在路上跑**（`true` = Nav2 正在带车赶路；`false` = 还没发车，或已到达原地停留中） |
| `cancelling` | **是不是正在等旧单子“刹停完”**（已喊 Nav2 取消，但还没收到 Nav2 的终结回调） |
| `token` | **发车单号**（每派一次新导航就 `+1`：1 号单、2 号单……用来防旧单子迟到的回调混进来） |

## 1. 队长怎么指挥传令兵（`Effect` 小纸条 + `drain()`）

**一句话作用**：把“业务规则”和“ROS2 通信”彻底拆开，让核心逻辑可以脱离 ROS2 单独测试和调试。

```text
任意事件进入 mission.hpp (submit / pause / tick / result / cancel_pending)
        │
        ▼
  只做两件事：改状态变量 + 往 effects 盒子里塞小纸条 (Start / Cancel / Record)
        │
        ▼  (每 50 ms 由 mission_node.cpp 调用 drain() 倒出并清空)
  if Start  ──→ start(e)  调 Nav2 发送导航目标
  if Cancel ──→ cancel()  调 Nav2 取消当前目标
  if Record ──→ 发布 /patrol/records + 写入 records.csv + 打印终端日志
```

**按顺序走一遍**：
1. **小纸条只有 3 种**：见 [mission.hpp L28-L34](../src/patrol_manager/include/patrol_manager/mission.hpp#L28-L34)，`Effect::Kind` 只有 `Start`（发车）、`Cancel`（刹车）、`Record`（记账）。
2. **队长只写纸条**：例如决定发车时，[mission.hpp L132-L134](../src/patrol_manager/include/patrol_manager/mission.hpp#L132-L134) 只会改 `flying = true`、`++token`，然后往 `effects` 里塞 1 张 `Start` 纸条和 1 张 `"dispatched"` 的 `Record` 纸条。
3. **传令兵统一执行**：[mission_node.cpp L306-L322](../src/patrol_manager/src/mission_node.cpp#L306-L322) 调用 `mission_->drain()` 一次取出所有纸条并清空盒子，用 3 个分支落地成 ROS2 动作。

**为什么这么设计**：
因为队长不碰任何 ROS2 API，所以在 [test_mission.cpp](../src/patrol_manager/test/test_mission.cpp) 写单元测试、或者用 GDB 调试 `cancel_pending` 时，根本不用起 Nav2 和仿真，几毫秒就能把所有状态切换跑完。

## 2. 系统启动与自动循环巡逻

**一句话作用**：拉起全部节点，确认定位与 Nav2 就绪后，按配置的航点一圈圈自动巡逻。

```text
run.sh → run_system.py → system.launch.py (拉起仿真 + Nav2 + 业务节点)
                                │
                                ▼
mission_node 每 50 ms tick()：检查 healthy() 且 nav_ready()
                                │ 都就绪后
                                ▼
mission.hpp 选 patrol/<patrol_index> → Start 派发 → 到达 DWELLING 停留 → patrol_index++ 循环
```

**按顺序走一遍**：
1. **统一组装启动**：[system.launch.py L49-L97](../src/patrol_bringup/launch/system.launch.py#L49-L97) 根据 `backend` 参数拉起底层（默认 `lightweight_sim` + 静态 TF `map→odom` + URDF；选 `gazebo` 时换成 TurtleBot3 + AMCL），再拉起 Nav2 6 大件、`mission_manager`、`velocity_guard` 和 `patrol_node`。
2. **启动自检**：[mission_node.cpp L290-L305](../src/patrol_manager/src/mission_node.cpp#L290-L305) 在 `tick()` 里确认两件事才放行：
   - `healthy()`：收到过合法 `/odom`，且距离上次收到不足 `odom_timeout_sec`（默认 1 秒）。
   - `nav_ready()`：每秒轮询一次 `bt_navigator/get_state`，确认 Nav2 生命周期已进入 `ACTIVE`（state id = 3），且 `/navigate_to_pose` Action Server 就绪。
3. **取出巡逻点并派发**：在 [mission.hpp L124-L135](../src/patrol_manager/include/patrol_manager/mission.hpp#L124-L135) 中，若 `active` 为空且报警 `queue` 也为空，就按 `patrol_index` 从 [mission.yaml L5](../src/patrol_bringup/config/mission.yaml#L5) 取出对应航点，生成 `patrol/0`、`patrol/1`……发 `Start` 纸条。
4. **到达 → 停留 → 切下一个点**：
   - Nav2 到达后回调 `result_callback(SUCCEEDED)` → [mission.hpp L147-L148](../src/patrol_manager/include/patrol_manager/mission.hpp#L147-L148) 置 `flying = false`、`handling = true`，状态进入 `DWELLING`，记录 `arrived`。
   - 停留满 `patrol_dwell_sec`（默认 1 秒）后，下一次 `tick()` 调 [finish()](../src/patrol_manager/include/patrol_manager/mission.hpp#L195-L200)：记录 `completed`，`patrol_index = (patrol_index + 1) % waypoints.size()`，清空 `active`。下一拍就会自动派发下一个点。

**为什么这么设计**：
`patrol_index` 只在**真正完成 (`finish()`)** 时才 `+1`。如果半路被报警抢占或暂停了，`patrol_index` 不变，恢复后会自动回到刚才没走完的那个巡逻点，不会漏点。

## 3. 速度控制与安全门禁（Nav2 → `velocity_guard` → 仿真底盘）

**一句话作用**：Nav2 算出的速度绝不直接发给车轮，必须过一层安全看门狗，保证“没许可、传感器断了、指令旧了”就立刻停车。

```text
Nav2 controller_server
   │ /raw_cmd_vel          (system.launch.py L85 重映射)
   ▼
Nav2 velocity_smoother
   │ /nav_cmd_vel          (system.launch.py L87 重映射)
   ▼
velocity_guard (guard.py)  ◀── 检查：/patrol/motion_permit + /nav_cmd_vel + /odom + /scan
   │ /cmd_vel              (底盘唯一速度出口)
   ▼
lightweight_sim (simulator.py)
   ├── 50 Hz step()：积分更新 (x, y, yaw) → 发 /odom + TF (odom → base_link)
   └── 10 Hz laser()：180 条射线求交      → 发 /scan (base_scan)
```

**按顺序走一遍**：
1. **话题重映射把口子收拢**：[system.launch.py L82-L90](../src/patrol_bringup/launch/system.launch.py#L82-L90) 把 Nav2 的速度出口全部重映射到 `/nav_cmd_vel`，让 `velocity_guard` 成为唯一能往 `/cmd_vel` 发速度的节点。
2. **心跳式运动许可**：`mission_manager` 每 50 ms 通过 [publish_permit()](../src/patrol_manager/src/mission_node.cpp#L227-L229) 发布 `/patrol/motion_permit`。只有同时满足 `flying && !cancelling && !paused && fault.empty() && healthy() && nav_ready()` 时才为 `true`。
3. **四路新鲜度看门狗**：[guard.py](../src/patrol_sim/patrol_sim/guard.py#L22-L28) 以 20 Hz 调 [guard_logic.py L24-L29](../src/patrol_sim/patrol_sim/guard_logic.py#L24-L29)：
   - 只要 `permitted == false`，或者 `nav_cmd_vel`、`motion_permit`、`odom`、`scan` **任意一路超过 0.5 秒没更新**，立刻输出 `(0, 0)` 停车。
   - 放行时还会把线速度限幅在 `±0.26 m/s`、角速度限幅在 `±1.0 rad/s`。
4. **仿真底盘闭环**：[simulator.py L41-L73](../src/patrol_sim/patrol_sim/simulator.py#L41-L73) 收到 `/cmd_vel` 后，用 [geometry.py](../src/patrol_sim/patrol_sim/geometry.py#L36-L45) 的 `integrate()`（带防穿墙碰撞检测）更新位姿发 `/odom` 和 `odom→base_link` TF，再用 `raycast()` 算出 180 束激光发 `/scan` 喂回给 Nav2。

**为什么这么设计**：
上层调度和看门狗完全不依赖具体底盘。切到 `backend:=gazebo` 或未来接树莓派真机时，只要替换最底下吃 `/cmd_vel`、吐 `/odom` 和 `/scan` 的那一层，上面整套导航和安全链一字不改。

## 4. 报警接入、校验、去重与排队

**一句话作用**：把外部发来的报警先过两道安检（格式安检 + 业务安检），合格的放进优先队列等调度，不合格或重复的留下审计记录。

```text
外部发 /patrol/incidents
        │
        ▼
mission_node::on_incident()  ──→ 计数 + 查 frame=="map" + 查四元数归一化
        │ 通过
        ▼
mission_->submit(task, now)  ──→ 查字段范围 + 查 known 去重 + 查队列上限 → 入 queue → 记 accepted
```

**按顺序走一遍**：
1. **ROS 层安检**：[mission_node.cpp L207-L226](../src/patrol_manager/src/mission_node.cpp#L207-L226) 的 `on_incident()` 先把 `incident_received_count_` 加 1（任务 1～2），然后检查两点：
   - `target.header.frame_id` 必须是 `map`；
   - 四元数模长平方必须在 `1 ± 0.05` 范围内。
   - 不合格直接记 `rejected` 返回；合格则把四元数转成 `yaw`，交给 `mission_->submit()`。
2. **业务层安检与入队**：[mission.hpp L62-L77](../src/patrol_manager/include/patrol_manager/mission.hpp#L62-L77)：
   - 校验 `id` 非空且不能以 `patrol/` 开头（避免和巡逻 ID 冲突）、`priority` 在 `1~100`、`ttl_sec` 与 `handling_sec` 合法。
   - 查 `known` 集合：出现过的 ID 直接记 `duplicate` 忽略（进程内去重）。
   - 查队列长度与历史 ID 数量上限（`max_queue=64`, `max_ids=10000`）。
   - 全部通过：记入 `known`，计算绝对过期时间 `expires = now + ttl_sec`，分配递增序号 `order = ++sequence`（保证同优先级先进先出），塞进 `queue`，记 `accepted`。
3. **排队过期清理**：每次 `tick()` 开头（[mission.hpp L104-L107](../src/patrol_manager/include/patrol_manager/mission.hpp#L104-L107)）会扫描 `queue`，超过 `expires` 还没派发的报警会被移除并记 `expired`。

**为什么这么设计**：
`on_incident()` **只负责入队，绝不直接发导航**。所有“要不要抢占、什么时候发车”全部统一收口到 50 ms 一次的 `tick()` 里判断，状态流转只有唯一入口，不会乱套。

## 5. 高优先级抢占、取消屏障与断点续巡

**一句话作用**：正在跑低优先级任务（巡逻或低优报警）时，如果队列里出现更高优先级报警，必须先安全刹停并确认旧导航彻底结束，再发新目标，做完后再接着干原来的事。

```text
tick() 发现 best()->priority > active->priority
        │
        ▼
suspend("preempt")：cancelling=true + 写 Cancel 纸条 + 立刻断 motion_permit 刹停
        │
        ▼  (取消屏障：cancelling==true 期间 tick() 直接 return，绝不抢发新目标)
Nav2 回调旧目标 result_callback (核对 token)
        │
        ▼
mission_->result()：flying=false, cancelling=false, requeue_active()
        │
        ▼  (下一拍 tick())
从 queue 挑最高优报警 → ++token → 写 Start 纸条派发 → 完成后自动恢复原任务
```

**按顺序走一遍**：
1. **触发抢占**：[mission.hpp L116-L118](../src/patrol_manager/include/patrol_manager/mission.hpp#L116-L118) 比较 `best()->priority > active->priority`（巡逻默认优先级 0，报警 1～100；同优先级按 `order` 先来后到）。满足条件就调用 [suspend(now, "preempt")](../src/patrol_manager/include/patrol_manager/mission.hpp#L172-L179)。
2. **分两种情况挂起**：
   - 如果车正在路上（`flying == true`）：把 `cancelling = true`，塞一条 `Effect::Cancel` 纸条（同时当拍 `permit()` 变 `false`，`velocity_guard` 瞬间刹停底盘）。
   - 如果车已经停在原地处理中（`flying == false`, `handling == true`）：不用向 Nav2 发取消，直接退出 `handling` 并 `requeue_active()`。
3. **显式取消屏障**：只要 `cancelling == true`，[mission.hpp L108-L113](../src/patrol_manager/include/patrol_manager/mission.hpp#L108-L113) 每次 `tick()` 都会直接 `return`（如果超过 `cancel_timeout_sec = 3s` 还没收到 Nav2 回复，就触发 `FAULT` 锁存）。
4. **旧目标终结与放回原任务**：Nav2 回调 [result_callback](../src/patrol_manager/src/mission_node.cpp#L253-L256) → 核对 `token == mission_->token` → 调 [mission_->result()](../src/patrol_manager/include/patrol_manager/mission.hpp#L136-L145) 清除 `flying` 和 `cancelling`，再调 [requeue_active()](../src/patrol_manager/include/patrol_manager/mission.hpp#L180-L184)：
   - 若被抢占的是**低优报警**：原样放回 `queue`（支持多层嵌套抢占，高优做完再回来做它）；
   - 若被抢占的是**巡逻点**：清空 `active`，但 `patrol_index` 不动，等所有报警清空后自动接着跑这个巡逻点。
5. **派发新目标**：下一拍 `tick()` 屏障解除，挑选 `queue` 里最优报警，`++token` 后发出 `Effect::Start`。

**为什么这么设计**：
如果不等旧 Action 终结就发新目标，旧目标迟到的 `SUCCEEDED / CANCELED` 回调很容易把新任务的状态冲坏。**取消屏障 + 递增 `token`** 是双保险：屏障保证同一时间 Nav2 里最多只有 1 个活目标，`token` 保证哪怕网络延迟送来旧回调也会被立刻丢弃。

## 6. 排队报警撤销（`cancel_pending`）

**一句话作用**：把还在 `queue` 里排队、尚未开始执行的报警撤掉，同时绝不误伤正在执行的任务，也防止同一个 ID 被重复提交。

```text
ros2 service call /patrol/cancel_pending "{id: 'alarm-001'}"
        │
        ▼
mission_node::cancel_pending_service_ 回调
        │
        ▼
mission_->cancel_pending(id) ──→ 在 queue 中找到则删除 + 记 pending_cancelled + 返回 true
                              ──→ 找不到（含正在 active 中）返回 false，不改任何状态
```

**按顺序走一遍**：
1. **服务接口**：[CancelPending.srv](../src/patrol_interfaces/srv/CancelPending.srv) 定义请求 `string id` 和响应 `bool success` / `string message`。
2. **服务接入**：[mission_node.cpp L129-L137](../src/patrol_manager/src/mission_node.cpp#L129-L137) 收到请求后直接转发给 `mission_->cancel_pending(req->id)`。
3. **业务删除规则**：[mission.hpp L79-L89](../src/patrol_manager/include/patrol_manager/mission.hpp#L79-L89) 只遍历 `queue` 查找匹配 `id`：
   - 找到：用 `queue.erase(it)` 移除该项，写一条 `pending_cancelled` 记录，返回 `true`（其余排队任务顺序不变）。
   - 没找到（包括这个 ID 正好是 `active` 活动任务）：直接返回 `false`。

**为什么这么设计**：
撤销时**故意不从 `known` 集合里删掉这个 ID**——撤销代表“这一单作废了”，不能让旧消息重放又把它重新塞进队列；同时不碰 `active`，把“撤销排队”和“中断当前导航”的边界划清。

## 7. 导航进度反馈与首帧距离修复（`FeedbackPath`）

**一句话作用**：在导航行驶期间按合适频率打印剩余距离，并且解决目标刚切换时 Nav2 首帧 `distance_remaining` 混用上一条路径的问题。

```text
start() 派发新目标 ──→ feedback_path_.reset(token, goal_stamp, "map", goal_xy)
                              │
Nav2 发布 /plan ──────────────┼──→ feedback_path_.update(...)（校验时间/坐标系/终点≤0.5m，预计算后缀距离）
                              │
Nav2 回调 feedback_callback ──┴──→ 4 条件防旧回调 → 限频 (报警1s / 巡逻5s) → 投影算剩余距离打印
```

**按顺序走一遍**：
1. **发车时绑定“指纹”**：[mission_node.cpp L242-L245](../src/patrol_manager/src/mission_node.cpp#L242-L245) 在 `start()` 里重置限频时间，并把当前 `token`、发车时间戳 `goal_stamp`、坐标系和目标点交给 `feedback_path_.reset()`。
2. **只收属于当前目标的 `/plan`**：[mission_node.cpp L108-L118](../src/patrol_manager/src/mission_node.cpp#L108-L118) 订阅全局路径 `/plan` 后调用 [feedback_path.hpp L24-L38](../src/patrol_manager/include/patrol_manager/feedback_path.hpp#L24-L38)：
   - 只有满足“`token` 匹配 + 路径时间戳晚于发车时间 + 坐标系匹配 + 路径终点距目标 ≤ 0.5 m”才会被接受，同时倒着算好每个路径点到终点的累积距离 `suffix_`。
3. **收到反馈先过滤、再限频、再算距**：[mission_node.cpp L257-L284](../src/patrol_manager/src/mission_node.cpp#L257-L284)：
   - **过滤旧回调**：`token != mission_->token || !flying || cancelling || !active` 直接扔掉。
   - **分级限频**：报警每秒最多打 1 次，普通巡逻每 5 秒打 1 次。
   - **估算剩余距离**：调 [feedback_path.hpp L40-L63](../src/patrol_manager/include/patrol_manager/feedback_path.hpp#L40-L63)，若新路径还没来（或位姿时间戳早于新路径），只打印一次 `WAITING_FOR_CURRENT_PLAN` 且不消耗限频窗口；就绪后把当前位置投影到最近折线段，算出 `点到线段距离 + 该段剩余 + suffix_[i+1]` 并打印 `source=current_plan`。

**为什么这么设计**：
`/plan` 话题本身不带 Action UUID，Nav2 刚切换目标时反馈里可能短暂带着上一条路径的长度。用“时间戳 + 终点容差”把 `/plan` 和当前 `token` 对齐，且明确只用于进度显示、不参与到达判定，既准确又不影响安全逻辑。

## 8. 旁路状态观察与摘要（`patrol_node`）

**一句话作用**：独立于主调度节点的轻量监控节点，专门听主系统状态并对外提供人类易读的 1 Hz 摘要和计数清零服务。

```text
mission_manager (每 50 ms 发布 /patrol/status)
        │
        ▼
patrol_node::on_status() ──→ status_received_count_++ + 缓存 last_status_ + 仅状态名变化时打印
        │
        ├── 1 Hz 定时器 publish_summary() ──→ 发布 /patrol/summary ("NO_STATUS" 或状态快照)
        └── /patrol/monitor/reset_count   ──→ 只清零 status_received_count_，保留最近状态缓存
```

**按顺序走一遍**：
1. **状态输入**：[mission_node.cpp L325-L330](../src/patrol_manager/src/mission_node.cpp#L325-L330) 在每次 50 ms `tick()` 末尾都会组装并发布 `/patrol/status`。
2. **订阅与去重打印**：[patrol_node.cpp L67-L83](../src/patrol_manager/src/patrol_node.cpp#L67-L83) 收到消息后累加计数、缓存最新快照 `last_status_`，只有当 `m->state != last_state_` 时才打印一条日志，避免 20 Hz 刷屏。
3. **定时摘要**：[patrol_node.cpp L86-L98](../src/patrol_manager/src/patrol_node.cpp#L86-L98) 每秒发布一次 `/patrol/summary`；连上主系统前输出 `NO_STATUS`，连上后输出 `state=... active_id=... queue_size=... received=...`。
4. **清零服务**：[patrol_node.cpp L41-L52](../src/patrol_manager/src/patrol_node.cpp#L41-L52) 提供 `/patrol/monitor/reset_count`（`std_srvs/srv/Trigger`），只把计数归零，保留 `last_status_` 防止摘要退回 `NO_STATUS`。

**为什么这么设计**：
旁路观察节点哪怕挂了、重启了，也完全不会影响 `mission_manager` 和 Nav2 的正常运行；这也是 ROS2 松耦合架构的典型用法。

## 9. 故障保护、急停锁存与人工恢复（`trip` / `recover`）

**一句话作用**：一旦发生影响安全的异常，立刻锁死系统并停车，绝不自动“瞎试”，必须等硬件/Nav2 恢复健康后由人工显式解锁。

```text
任意异常触发 (odom超时 / Nav2掉线 / 取消超时 / 巡逻重试耗尽 / 人工急停 / 日志写入失败)
        │
        ▼
mission_->trip(reason) ──→ 锁存 fault + 立刻断 motion_permit + suspend("fault") 取消导航
        │
        ▼  (故障期间 tick() 不派新任务，不会自愈)
传感器与 Nav2 恢复正常 + 旧导航彻底终结 (!flying && !cancelling)
        │
        ▼
人工调用 /patrol/recover ──→ mission_->recover(healthy() && nav_ready()) ──→ 清空 fault
```

**按顺序走一遍**：
1. **哪些地方会触发 `trip()`**（锁存第一个故障原因，后续故障不会覆盖它）：
   - `/odom` 断流超 1 秒：[mission_node.cpp L303](../src/patrol_manager/src/mission_node.cpp#L303)
   - 导航中 Nav2 生命周期或 Action Server 掉线：[mission_node.cpp L304](../src/patrol_manager/src/mission_node.cpp#L304)
   - 取消导航超过 3 秒无回应：[mission.hpp L109-L111](../src/patrol_manager/include/patrol_manager/mission.hpp#L109-L111)
   - 巡逻点导航失败次数用完（不静默跳过）：[mission.hpp L190-L193](../src/patrol_manager/include/patrol_manager/mission.hpp#L190-L193)
   - 人工调用 `/patrol/emergency_stop`：[mission_node.cpp L138-L142](../src/patrol_manager/src/mission_node.cpp#L138-L142)
   - CSV 审计日志写入失败：[mission_node.cpp L323](../src/patrol_manager/src/mission_node.cpp#L323)
2. **故障锁存反应**：[mission.hpp L95-L98](../src/patrol_manager/include/patrol_manager/mission.hpp#L95-L98) 记录 `fault` 原因，调用 `suspend(now, "fault")`；`permit()` 立刻变 `false` 让 `velocity_guard` 刹停。
3. **严格恢复门槛**：调用 `/patrol/recover`（[mission_node.cpp L150-L154](../src/patrol_manager/src/mission_node.cpp#L150-L154)）→ [mission.hpp L99-L102](../src/patrol_manager/include/patrol_manager/mission.hpp#L99-L102) 必须同时满足 `healthy() && nav_ready() && !flying && !cancelling` 才允许清空 `fault`。而且清空 `fault` 时**不会改动 `paused`**（如果之前手动暂停了，恢复故障后仍保持暂停，防止车突然窜出去）。

**为什么这么设计**：
这是工业机器人典型的 **Fail-Safe（故障导向安全）** 原则：异常发生时第一时间断动力，且永远由人确认现场安全后再按恢复键。

## 10. 按 `Ctrl+C` 时的优雅退出

**一句话作用**：防止直接强杀进程导致 Nav2 生命周期节点报错卡死、或底盘还带着残留速度继续滑行。

```text
终端按 Ctrl+C
        │ (被 run_system.py 拦截，不直接转发给所有 ROS 节点)
        ▼
1. 循环调用 /patrol/prepare_shutdown  ──→ 暂停任务 + 等到 !mission_->flying（旧导航彻底终结）
        │
        ▼
2. 调用 lifecycle_manager_patrol/manage_nodes (SHUTDOWN)  ──→ 按逆依赖顺序关闭 Nav2 6 大件
        │
        ▼
3. 向 ros2 launch 进程发 SIGINT（超时再 SIGTERM / SIGKILL）
```

**按顺序走一遍**：
1. **外层监管拦截信号**：[run.sh](../scripts/run.sh#L10) 启动的是监管脚本 [run_system.py](../scripts/run_system.py#L59-L91)，它把 `ros2 launch` 放在独立会话（`start_new_session=True`）里跑，所以你按 `Ctrl+C` 时信号先到 `run_system.py`，不会一下子把所有 ROS 上下文同时拍死。
2. **第一步：先停任务**：[run_system.py L46](../scripts/run_system.py#L46) 反复调用 `/patrol/prepare_shutdown`（[mission_node.cpp L143-L149](../src/patrol_manager/src/mission_node.cpp#L143-L149)），先暂停并断掉 `motion_permit`，只有当 `!mission_->flying`（旧 Action 已拿到终结结果）才返回 `success = true`。
3. **第二步：逆序关 Nav2**：[run_system.py L47-L52](../scripts/run_system.py#L47-L52) 通知 `lifecycle_manager_patrol` 执行 `SHUTDOWN`，让 Nav2 从上到下有序销毁内部 Action 和控制器。
4. **第三步：安全退场**：最后再发 `SIGINT` 结束 `ros2 launch`；同时 [guard.py L52-L55](../src/patrol_sim/patrol_sim/guard.py#L52-L55) 退出前还会再补发一帧全零 `Twist()` 给 `/cmd_vel` 确保车停稳。

**为什么这么设计**：
如果在 Nav2 正在执行导航时直接 `SIGINT` 强杀，BT 行为树和控制器常会因为上下文已销毁而抛出大量异常甚至僵尸进程。先“停业务 → 关 Nav2 → 杀 launch”三步走，退出干净利落。

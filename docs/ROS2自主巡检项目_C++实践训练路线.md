## 1. 当前起点与训练目标

你已经完成 ROS2 基础通信机制学习，以及自主巡检项目核心源码调用链梳理。目前能够运行项目，理解 Topic、Service、Action、Timer 的职责，并大致看懂报警进入队列、派发和执行导航的过程。

当前能力边界是：**项目能运行、核心源码大致能看懂，但独立 C++ 开发能力仍需通过实际编码建立。**

已经完成的基础包括：

- ROS2 常用 CLI 操作及节点、话题、服务、动作的基本认识。
- 六课源码学习：Topic 订阅、Service 服务端、Action 客户端、Timer、业务逻辑、整体调用链。
- 启动巡检系统，发送报警，暂停与恢复，观察状态和任务记录。
- 初步理解类、成员函数、智能指针、Lambda、`auto`、容器和流程控制。

下一阶段集中补足三项能力：

1. **组织代码**：自己确定成员变量、函数参数、返回值和回调之间的关系。
2. **完成开发闭环**：修改、编译、重启、验证，并确认运行的是新程序。

课堂介绍过的修改实验不默认已经完成；现有代码或骨架也不默认代表个人独立开发成果。下面所有任务均从“尚未验收”开始。

- 以当前巡检项目为主要载体，每次只增加一个核心知识点或一项小功能。

## 4. 第一阶段：独立修改现有代码

### 任务 1：给报警接收回调增加计数

**功能需求**

每进入一次报警回调，接收次数加一，并打印接收次数、报警 ID 和优先级。统计口径为“收到消息”，因此重复消息和随后被拒绝的消息也计数。每次节点进程启动时从零开始。

**需要掌握**

- 成员变量初始化、整数类型和 `++`。
- 局部变量与成员变量的生命周期。
- 日志参数与格式的类型匹配，包括字符串的输出。

**修改文件**

- `src/patrol_manager/src/mission_node.cpp`：报警回调和类的成员声明。

**开发提示**

先找回调入口，再检查哪些分支会提前 `return`。自己判断计数成员和递增语句分别应该放在哪里。

**编译、运行和验证**

1. 按第 8 节编译并重启主系统。
2. 使用现有服务暂停系统，等待旧导航终结。
3. 依次发送合法 A、合法 B、重复 A、优先级为 0 的 C；每条消息的其他字段均合法，A、B、C 使用本次进程中尚未使用的 ID。
4. 接收计数应增加四次；原有任务记录应出现两次 `accepted`、一次 `duplicate`、一次 `rejected`。
5. 重启节点，检查接收计数重新开始。

**验收能力**

能独立完成一个成员变量与回调的小修改，并解释“收到四条消息”与“接收两个任务”的区别。

### 任务 2：把报警处理提取成成员函数

**功能需求**

将现有报警 Lambda 中的处理逻辑移入一个具名成员函数。订阅处的 Lambda 负责调用该函数，业务行为保持一致。

**需要掌握**

- `this` 的用途，以及通过 Lambda 调用成员函数。
- 函数参数怎样传递消息，成员函数怎样访问节点状态。

**修改文件**

- `src/patrol_manager/src/mission_node.cpp`。

**开发提示**

先自己写出函数签名，再移动函数体。继续沿用现有消息指针类型和简单的 Lambda 转发方式。

**编译、运行和验证**

1. 编译并重启，重复任务 1 的四条输入。
2. 另外发送一个合法报警，观察其完整执行。
3. 对比修改前后：计数、校验、拒绝、派发和完成行为应一致。

**验收能力**

能确定一个成员函数的签名，完成保持行为不变的代码整理，并验证整理没有引入功能变化。

## 6. 第三阶段：实现排队报警撤销功能

业务需求：操作员能够按 ID 撤销尚在队列中的报警。先实现和测试纯 C++ 规则，再接入 ROS2 服务。

### 任务 6：先在业务层实现撤销

**功能需求与边界**

- 根据 ID 删除队列中的对应报警，返回是否成功。
- 找不到时返回失败，队列保持原样。
- 当前活动任务保持原样，不触发当前导航取消。
- 其他排队任务保留原有顺序与调度规则。
- 撤销后的 ID 仍保留既有去重记录，同一进程中再次提交仍视为重复。
- 成功撤销产生独立记录，例如 `pending_cancelled`，与已有导航取消记录区分。
- 队列中的已中断报警也属于可撤销范围；巡逻任务按既有方式管理。

**需要掌握**

- `const std::string &`、布尔返回值。
- `std::vector` 遍历、迭代器和 `erase()`。
- 删除后的迭代器失效问题。
- 将需求转化为正常、失败及边界测试。

**修改文件**

- `src/patrol_manager/include/patrol_manager/mission.hpp`。
- `src/patrol_manager/test/test_mission.cpp`。

**开发提示**

实现前先写出函数输入、返回值和规则。沿用现有测试辅助函数，通过传入时间驱动业务，无需真实等待导航。

**编译与验证**

按第 8 节编译并运行核心测试，至少覆盖：

1. 空队列。
2. 不存在的 ID。
3. 删除队列中间任务。
4. 删除后其他任务顺序保持。
5. 活动任务不被删除。
6. 撤销 ID 再提交仍被去重。
7. 成功撤销记录的类型与任务 ID 正确。

先让这一项测试通过，再接 ROS2 服务。

**验收能力**

能将文字需求实现为一个 C++ 函数，并用自动测试证明它满足边界约定。

5. 保留命令、日志、实际结果和代码差异。

**验收能力**

能展示需求、实现、测试和排障过程；能解释自己的主要修改及其适用边界。实际遇到的错误如实记录，GDB 练习单独标记为调试练习。

## 8. 统一编译、运行与测试流程

Windows 项目根目录为 `D:\4work\3project\ROS2_patrol_robot`，用于本地源码和文档管理。以下命令均在已经可以运行的 Ubuntu 工程根目录执行；先切换到实际的 Ubuntu 工程目录，再进行编译和启动。

### 8.1 日常构建

```bash
source /opt/ros/humble/setup.bash

colcon build --packages-up-to patrol_manager --symlink-install \
  --cmake-args -DBUILD_TESTING=ON

source install/setup.bash
```

`--packages-up-to patrol_manager` 会构建任务包及其工作空间依赖。任务 7 修改接口后也使用这条命令，重新生成接口并构建使用方。

构建成功后停止旧进程，再启动主系统，避免继续观察旧程序：

```bash
bash scripts/run.sh rviz:=false
```

任务 3～8 的观察节点可先在另一个终端独立运行。每个新终端都加载环境：

```bash
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 run patrol_manager patrol_node
```

任务 9 将观察节点接入 Launch 后，由启动入口统一启动，避免再手动重复启动。

### 8.2 核心测试

修改业务核心或测试后，先完成构建，再执行：

```bash
colcon test --packages-select patrol_manager \
  --event-handlers console_direct+
colcon test-result --verbose
```

构建成功与测试通过分别确认。首次运行测试前，确保构建时启用了 `BUILD_TESTING`。

### 8.3 Debug 与启动集成构建

需要调试时，可在日常构建命令的 CMake 参数中增加 `-DCMAKE_BUILD_TYPE=Debug`。随后通过调试器运行核心测试，在自己新增的函数处断点并检查变量。

任务 9 修改启动文件后执行全工程构建：

```bash
colcon build --symlink-install \
  --cmake-args -DBUILD_TESTING=ON -DCMAKE_BUILD_TYPE=Debug
source install/setup.bash
```

### 8.4 ROS2/Nav2 集成验收

在一个终端启动轻量模式：

```bash
bash scripts/run.sh rviz:=false panel:=false
```

在另一个已加载环境的终端，从工程根目录运行：

```bash
python3 tools/ros_acceptance.py
```

现有结果写入 `test_results/ros_acceptance.json`。任务 9 需要让新增场景也能明确报告成功或失败。

纯 C++ 测试用于验证业务规则；实际 ROS2/Nav2 运行用于验证通信与集成。本文提供验证要求，实际 Ubuntu 运行结果需由你执行后填写。

## 9. 遇到问题时怎样推进

### 编译错误

1. 先读第一条有效错误，找到文件、行号和涉及的类型或符号。
2. 判断它属于语法、声明、类型、依赖还是链接问题。
3. 做一处最小修改后重新编译，观察第一条错误是否变化。
4. 求助时提供第一条有效错误及相关上下文代码。

### 运行行为不符合预期

1. 确认构建成功、环境已加载、旧进程已停止。
2. 写清输入、预期结果和实际结果。
3. 缩减为最少节点、最少消息能够复现的场景。
4. 使用日志或断点确认回调是否进入、分支是否执行、成员数据怎样变化。

### 向 Codex 求助的模板

```text
我目前的判断：

```
